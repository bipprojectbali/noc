# CLAUDE.md — NOC wall

Dinding pane berpetak; tiap pane memegang satu atau beberapa situs (semuanya ter-mount, satu aktif). Bun (server + bundler + test runner) · React 19 · react-router 8 **library mode** · zustand 5 · Tauri 2 (`unstable`, multiwebview) · SQLite via `bun:sqlite`. v0.2.0.
README = produk & milestone untuk manusia. File ini = perintah, invariant, jebakan. Jangan saling duplikasi.

## Perintah

- `bun install` · `bun run dev` (hot, http://127.0.0.1:7788) · `bun run start` (tanpa hot)
- `bun test` (31 file `*.test.ts(x)` di `tests/`) · `bun run typecheck` (`tsc --noEmit`)
- `bun run build:sidecar` → `scripts/sidecar.build.ts` menghasilkan `src-tauri/binaries/noc-server-<triple>`; triple dari `rustc --print host-tuple`
- `bun run tauri:dev` / `tauri:build` — keduanya menjalankan `build:sidecar` lewat `beforeDevCommand`/`beforeBuildCommand`
- `bun run build:binary` → `dist/noc` standalone, **bukan** yang dipakai Tauri

`src/server/server.entry.ts` satu-satunya entrypoint server (dev, binary, sidecar). `src/app/app.css` satu-satunya stylesheet, semua kelas ber-prefix `noc-`.

**`app.css` 689 baris — lewat batas keras 500 baris aturan global, dan itu keputusan sadar, bukan kelalaian.** Aturan project menang atas aturan global saat bentrok, dan di sini keduanya memang bentrok: satu stylesheet tunggal adalah invariant project (urutan cascade dapat diprediksi, nol pertanyaan "file mana yang menang"), sementara batas 500 baris mengasumsikan file logika yang bisa dipecah per tanggung jawab. Memecah CSS ini berarti memecah cascade-nya. Catatan ukuran yang jujur: 689 baris / 19.518 karakter — **batas karakter (20.000) tinggal 482 karakter (~2,4%), jadi tambahan berikutnya yang lebih besar dari satu rule pendek sudah memicu pemecahan, bukan lagi pengecualian**. Rencana saat itu tiba: pecah per layer (`app.base.css` / `app.pane.css` / `app.drag.css`) dengan satu file pengimpor berurutan — jangan pecah per komponen, dan jangan tempel `<style>` di komponen.

**`src/pane/pane.webview-renderer.ts` 398 baris — lewat batas 300 baris untuk service/use-case, dan itu juga keputusan sadar.** Angka jujurnya: 398 baris / 14.940 karakter, dari situ 124 baris komentar + 37 baris kosong, jadi **237 baris kode** — dan angka itulah yang penting: ia tidak bergerak satu baris pun saat file tumbuh dari 379 ke 398. Yang tumbuh seluruhnya komentar. Jadi file ini lewat batas bukan karena logikanya menumpuk, tapi karena invariant-nya mahal untuk dijelaskan, dan itu memperkuat kesimpulan di bawah bukan melemahkannya: memecah file tidak menghapus satu pun dari 237 baris itu, hanya memindahkannya, sementara komentar yang harus menjelaskan sambungan antar-file justru lebih panjang daripada yang sekarang menjelaskannya di satu tempat. Terhadap batas keras global ia di 80% baris dan 75% karakter. Batas 300 mengasumsikan file yang bisa dipecah per tanggung jawab, dan di sini tanggung jawabnya satu: `Map<SiteId, PaneEntry>` dengan satu `send()` yang memegang dedupe rect, `visible && active && capturing && hasArea`, dan urutan optimistic-`sent`-lalu-koreksi. Kesembilan method publiknya adalah mutasi pendek yang semuanya bermuara di `send()` atau `open()`. Memecah "pembukuan" dari "pengiriman" menuntut `PaneEntry` — pemilik `sent` dan `opened` — pindah ke sisi pengirim, lalu satu objek konteks buatan untuk membawa `capturing` menyeberang batas file: ditulis `setCursorCapture`, dibaca `send`. Itu potongan, bukan sambungan. Dua kandidat lain terkunci lebih keras: `createWebviewPointerSuppressor` mendaftar sebagai efek samping saat modul diimpor, jadi file sendiri berarti tak ada yang mengimpornya, suppressor tak pernah terdaftar, dan drag splitter mati senyap; sedangkan komponen anchor duduk bersama renderer-nya sama seperti `PaneIframe` di `pane.iframe-renderer.tsx`, dan memindahkan hanya milik webview membuat dua jalur renderer asimetris tanpa alasan fungsional. **Pemicu pemecahan bukan angka 300, tapi state machine level situs kedua yang mendarat di sebelah `send()`.** Rencana saat itu tiba: pecah per **penerima alamat**, bukan per lapis — file ini menyimpan peta situs + pengiriman ke bridge, dan apa pun yang dialamatkan per pane (`place`, `release`) pindah keluar. Jangan pecah pembukuan vs pengiriman, dan jangan pindahkan suppressor.

## Invariant yang tidak boleh dilanggar

**1. Iframe tidak boleh berganti parent DOM.** Ganti parent = React bikin node baru = halaman reload. Maka:

- `src/layout/layout.renderer.tsx` merender pohon sebagai flex bersarang yang daunnya **div kosong** ber-`data-pane-slot`. Div kosong itu BUKAN bug — menaruh konten di situ mengikat DOM pane ke bentuk pohon.
- Pane hidup di satu flat list di `src/pane/pane.layer.tsx`, urutannya selalu creation order (`createdAt`, tie-break `id`) dan tidak pernah berubah. Jangan pindahkan pane ke dalam pohon layout, jangan urutkan ulang list ini.
- `src/geometry/geometry.sync.ts` menyalin rect slot ke host pane secara imperatif (`useLayoutEffect` + `ResizeObserver` di `src/app/app.shell.tsx`), memakai `transform: translate(...)` (`geometry.rect.ts:rectToStyle`), bukan `left`/`top`. Jangan posisikan pane lewat state React.
- `splitPane` (`src/layout/layout.tree.ts`) **wajib** mempertahankan id pane asal; hanya split node + pane baru yang dapat id baru.
- Hal yang sama berlaku untuk `movePane`/`swapPanes` (`src/layout/layout.move.ts`) — itulah satu-satunya alasan seret pane tidak me-reload halaman. `movePane` memang mencetak id **split** baru lewat `makeId`, tapi tak pernah id pane; guard `pane.parentId === null` ada supaya `detachLeaf` tak pernah mencapai cabang reseed-nya (cabang itu mencetak pane baru). `swapPanes` tak butuh `makeId` sama sekali: ia hanya menukar slot anak + `parentId`, bentuk pohon dan `sizes` tetap utuh.
- `rearrangePane` di `pane.store.ts` melakukan satu `set` untuk seluruh perpindahan. Detach lalu insert dalam dua commit menyisakan satu frame di mana pane tak punya slot, dan pane tanpa slot disembunyikan — webview-nya berkedip. Penolakan (`pane-docked`, `pane-not-in-tree`) meninggalkan dinding apa adanya.
- **Urutan di `syncPaneGeometry` tidak komutatif: tulis transform host dulu, `place?.()` terakhir.** Renderer di luar DOM mengukur anchor yang hidup *di dalam* host itu, jadi dipanggil duluan ia membaca rect sebelum pane pindah. Untuk dua pane berukuran sama yang bertukar tempat, rect basi itu sama persis dengan yang terakhir dikirim, dedupe renderer membuangnya, dan webview-nya tak pernah pindah. Tidak ada yang mengoreksi sesudahnya: sync kedua datang dari `ResizeObserver`, dan tukar-tempat antar pane seukuran tidak mengubah ukuran apa pun.
- Pane tanpa slot disembunyikan (`visibility: hidden`), bukan diberi rect nol — viewport nol membuat halaman reflow dan kehilangan scroll.
- `useShallow` di `usePaneIdsInCreationOrder` wajib; tanpa itu seluruh pane layer re-render tiap perubahan store.
- **Satu pane memegang daftar situs, dan semuanya ter-mount sekaligus** di satu grid cell `.noc-pane__body` (`grid-template-areas: "stack"`), satu `renderer.Content` per situs ber-`key={site.id}`. Yang tidak aktif **disembunyikan**: iframe lewat `noc-pane__frame--hidden` (`visibility`), webview lewat flag `visible` yang sudah ada. Berpindah situs = satu tulisan tree (`setActiveSite`), bukan unmount dan bukan `pane_webview_close` — alasan yang sama dengan pane tanpa slot: rect nol atau unmount berarti reload, scroll hilang, sesi hilang. `releaseSite` hanya untuk situs yang benar-benar dibuang — ia dipanggil dari `dropSite`, dan `dropSite` melayani `removeSite` maupun `clearPane` — plus `deletePane` yang membawa seluruh situs pane itu sekaligus.
- **Konsekuensi: webview dikunci per `siteId`, bukan per pane.** `src/pane/pane.webview-renderer.ts` menyimpan `Map<SiteId, …>` dan label yang dikirim ke Rust adalah site id (argumen `invoke` tetap bernama `paneId`, jadi pengalihan per-situs itu sendiri nol perubahan di `src-tauri/`). `place(paneId, visible)` tetap bicara per pane dan menyebar rect yang sama ke tiap situs pane itu dengan `visible && active`. `state.load` juga dikunci per `siteId`: status muat milik halaman, bukan milik pane. Selector `paneLoadState`/`siteLoadState` ada di `pane.store-sites.ts`, bukan di `pane.store.ts`.

**2. Penolakan framing tidak bisa dideteksi dari client.** Iframe terblokir `X-Frame-Options` tetap memicu `load` di Chromium dan dokumennya tak terbaca. Maka:

- Klasifikasi server-side: `GET /api/embeddability?url=` → `src/server/embed.probe.ts` (fetch target, `body.cancel()`, timeout 8 s) → `src/embed/embed.classifier.ts` (`X-Frame-Options` + CSP `frame-ancestors`). Di jalur **langsung** (pane menunjuk origin aslinya) tetap tak ada satu pun header target yang di-strip atau ditulis ulang — penolakan dilaporkan ke user, bukan diakali.
- **Di jalur proxy, bagian "tidak ada header yang ditulis ulang" dicabut — sadar, atas perintah eksplisit, dan bukan demi mengakali penolakan framing.** Sebabnya ada di invariant 6: cookie sesi tak pernah kembali ke iframe cross-site, dan satu-satunya jalan dalam app adalah membuat situs **same-site** dengan halaman dinding. Begitu trafiknya lewat host dinding, `X-Frame-Options` toh tak bisa lagi menolak apa pun — dinding *adalah* originnya. Jadi hilangnya penolakan framing adalah efek samping yang diterima, bukan tujuan. Konsekuensi yang harus jujur: `/api/embeddability` menjawab `verdict: "unknown"` untuk situs yang akan di-frame lewat host dinding (`createEmbeddabilityHandler` di `server.routes.ts`) — menjawab `refused` di situ akan jadi bohong. Daftar lengkap header yang disentuh beserta alasan per baris ada di `src/proxy/proxy.headers.ts`; jangan tambah entri tanpa alasan tertulis di situ juga.
- State pane = reducer murni `src/pane/pane.load-state.ts`: `empty → probing → loading | refused → ready`. Tiap event membawa `url`-nya agar hasil probe untuk alamat lama dibuang. Jangan menambah pembacaan `iframe.contentDocument` atau timer "kalau belum load berarti ditolak".
- Verdict `unknown` sengaja optimistis → `loading`; `probe-failed` juga.
- UI refusal hanya untuk renderer iframe (`framingApplies` di `pane.frame.tsx`); webview native adalah dokumen top-level, batas itu tak berlaku di sana. Teks refusal bercabang pada `isNativeHost()`: di shell ia menyarankan pindah renderer, di browser ia bilang jalan keluarnya cuma ada di desktop app.
- Pane yang benar-benar dirender sebagai webview **tidak** diprobe (`probe` di `pane.store.ts`): fetch-nya takkan dibaca siapa pun. Pane tetap harus keluar dari `probing`, jadi store langsung mengirim `probe-settled` dengan verdict `unknown`.

**3. Child webview native adalah view level OS.** Selalu melukis di atas layer web, mengabaikan CSS clipping dan `pointer-events`. Maka:

- **Chrome permanen pane = satu kotak mengambang (⋮ + pip situs), satu bentuk untuk kedua renderer.** `src/pane/pane.menu.tsx` tidak lagi punya prop `floating`; kelasnya selalu `.noc-pane__chrome` — `position: absolute`, pojok kanan atas, **nol tinggi terpakai**. Label host sudah dihapus — ia hidup sebagai `title` tombol, nol piksel.
  **Sejarah, supaya tidak diputar ulang:** dulu bentuknya bercabang per renderer. Pane webview native mendapat seam `--noc-seam-height` (20 px): satu baris yang direservasi di atas halaman, tempat tombol duduk sebagai **sibling** anchor, karena overlay permanen di atas webview memang tidak akan terlihat sama sekali. Alasan itu masih benar; yang salah adalah harganya. Ruang yang direservasi — bukan warnanya — itulah yang membuat batas antar-pane terbaca lebar dan dinding terlihat dijahit dari kotak-kotak. Sebelumnya sudah gagal pula: dua baris permanen (URL bar + baris kontrol) dan strip berlabel.
  **Yang menggantikannya: chrome pane webview adalah webview kedua.** Shell memarkir satu child webview transparan **88×40** di pojok kanan atas rect pane (`CHROME_WIDTH`/`CHROME_HEIGHT` di `src-tauri/src/pane_webview.rs`), **dibuat sesudah** webview halaman karena wry menempelkan tiap anak dengan `addSubview` — urutan buat = urutan lukis. Ia memuat `/pane-chrome` dari origin wall sendiri (`src/server/server.chrome-page.ts`), jadi ia **sama-origin** dengan halaman wall dan keduanya bicara lewat `BroadcastChannel` (`src/pane/pane.chrome-channel.ts`) — nol `invoke` kelima, nol `emit`/`listen`. Ia membawa **⋮ dan pip sekaligus**, bukan cuma ⋮: pip adalah satu-satunya kontrol multi-situs yang tak menuntut membuka menu, dan menjatuhkannya berarti menukar keluhan kosmetik dengan fitur yang hilang.
  Dua aturan yang mahal kalau dilanggar: (1) **`ensure_chrome` dipanggil dari `place_pane` saja, bukan dari `pane_webview_show`.** `show` pertama tiap situs datang dengan rect 0×0 — halaman wall membuka semua situs sebelum dinding diukur — jadi `chrome_corner()` menjawab `None` dan chrome tak pernah lahir; halaman selamat karena `place` berikutnya mengoreksinya, chrome tidak. (2) **Jangan pakai `get_webview_window(WALL_WINDOW_LABEL)` di mana pun.** Tauri hanya menjawabnya untuk window yang memegang tepat satu webview, jadi begitu pane pertama jadi anak window wall, lookup itu mengembalikan `None` padahal window-nya jelas ada. Pakai `app.get_window(...)` (window) atau `app.webviews().get(...)` (webview-nya).
  Harganya, disengaja dan tercatat: **88×40 pojok kanan atas halaman mati untuk klik** — rect webview menelan semua klik di dalamnya, tidak seperti padding kotak DOM yang tembus pointer — dan dibayar juga oleh pane satu-situs yang tak menampilkan pip. Jalur naiknya ada di komentar `ponytail:` pada konstanta itu. Jangan samakan kedua renderer jadi satu cabang global di sisi lain: satu dinding bisa memuat keduanya sekaligus, dan pane iframe tidak punya (dan tidak butuh) webview chrome.
- **Panel menu (`src/pane/pane.menu-panel.tsx`) adalah pengecualian overlay yang disengaja — jangan "betulkan" jadi sibling.** Ia `position: absolute` di bawah tombol (lebar tetap 224 px, rata kanan), dan izinnya datang dari satu hal: selama panel terbuka, `suspendPanePointerCapture()` menyembunyikan **semua** webview di dinding (seam yang sama dengan drag splitter — tanpa `invoke` keempat, tanpa native menu). Konsekuensinya disengaja dan diterima: buka satu menu, semua pane webview blank. Hide ≠ destroy, jadi halaman tetap jalan dan balik di posisi scroll yang sama. Satu `useEffect` di `pane.menu.tsx` memegang suppressor selama `open` dan melepasnya di cleanup — itu menutup **semua** jalan tutup (tombol lagi, Escape, klik luar, submit, split, pane dihapus saat menu terbuka). Jangan lepas suppressor manual per call site; menduplikasi pelepasan = depth count bocor. `useEffect` kedua memberi perilaku dropdown: fokus masuk ke field URL saat buka, balik ke tombol ⋮ saat tutup.
- **Seret pane adalah pemakai ketiga `suspendPanePointerCapture`, setelah drag splitter dan menu panel.** Pegangannya tombol ⋮, dan itu satu-satunya kandidat: badan pane tak bisa didengar sama sekali (iframe cross-origin menahan event di dokumennya sendiri, webview native mengambil mouse di level OS). Ambang `DRAG_THRESHOLD_PX` = 4 px radial (`Math.hypot`) adalah seluruh pembeda antara "buka menu" dan "seret"; klik yang mengekor seret ditelan di `usePaneDragHandle` (`event.detail > 0` — klik dari keyboard `detail === 0` selalu diloloskan). Suppressor dipegang oleh **satu** `useEffect` ber-key "apakah pane ini yang sedang diseret", jadi tiap jalan keluar (drop, Escape, `window.blur`, `pointercancel`, pane dihapus di tengah seret) melepasnya sekali, tepat sekali. Jangan lepas manual di call site; itu membocorkan depth count — aturan yang sama dengan menu panel.
- **`pane.drop-overlay.tsx` adalah overlay kedua yang diizinkan, dan izinnya lebih kuat daripada menu panel:** ia hanya ada selama seret berlangsung, dan selama itu semua webview native tersembunyi — tak ada lagi view level OS yang bisa melukis di atasnya. Di luar jendela itu ia merender `null`. `pointer-events: none` di seluruhnya wajib: target drop dicari dengan `document.elementFromPoint` → `closest("[data-pane-host]")`, dan overlay yang menjawab akan membuat setiap drop mendarat di pane asal. Overlay dipasang sebagai **sibling** `PaneFrame` di `pane.layer.tsx`, bukan anaknya — ia harus menutupi chrome pane, dan berlangganan store di sini menjaga elemen tempat halaman hidup tidak ikut re-render tiap gerak pointer. Tiap pane (bukan cuma dua yang terlibat) diberi ring + label host karena dinding campuran menampilkan pane webview sebagai kotak kosong dan pane iframe tetap berisi; tanpa label, kotak kosong itu terbaca sebagai "rusak", bukan "pane".
- Aritmetika drop tinggal di `pane.drag-geometry.ts`, nol DOM: `CENTER_ZONE_FRACTION` = 0.3 → zona tengah = 40% tiap sumbu, batas antar-tepi jatuh di diagonal (sudut jadi tak memihak satu sumbu), titik di luar rect tetap jatuh ke tepi terdekat, rect degenerate → `center`. Alasan tengah dibuat lebih kecil dari empat tepi: swap memindahkan dua pane, jadi salah-swap lebih mahal daripada salah-tepi. Dipisah dari `pane.drag.ts` karena hanya bagian aritmetika inilah yang bisa dibuktikan tanpa browser (lihat "Jebakan test").
- **Klik kanan hanya bisa di permukaan milik app sendiri:** kotak chrome (`pane-chrome-`) dan pesan pane kosong (`pane-empty-`). Di atas konten halaman mustahil — iframe cross-origin tak pernah menyerahkan `contextmenu` ke parent, dan webview native mengambil event di level OS sebelum layer web melihatnya. Ini batas platform, bukan pekerjaan yang terlewat; jangan coba tambal dengan overlay penangkap event (overlay itu sendiri tak terlihat di atas webview).
- State `menuOpen` tinggal di `pane.frame.tsx`, bukan di `pane.menu.tsx`, karena pesan pane kosong juga membukanya.
- **Hide ≠ destroy.** `pane_webview_place(..., visible=false)` mempertahankan halaman; membuat ulang webview = reload, persis yang desain ini cegah. `pane_webview_close` hanya punya tiga pemanggil, semuanya membuang halaman untuk selamanya: `releasePane` dari `deletePane` dan dari `setPaneStrategy` saat pane pindah dari webview ke iframe (React tak bisa melepas view yang tak pernah ada di DOM), plus `releaseSite` lewat `dropSite`, yang membuang satu halaman sementara pane-nya tinggal. Tiga pemanggil di sisi web, tapi **empat jalan masuk dari store**: `dropSite` melayani `removeSite` **dan** `clearPane`. Jangan tambah pemanggil keempat tanpa alasan sekuat itu — khususnya jangan untuk berpindah situs.
- **`chrome_height()` (`src-tauri/src/pane_webview.rs`) wajib baca AppKit, bukan selisih ukuran window.** Title bar style default Tauri = `fullSizeContentView`, jadi content view membentang sepenuh frame dan `outer_size - inner_size` selalu 0 di macOS — itulah kenapa koreksi aritmetika sebelumnya diam-diam tak berefek. Angka yang benar: `contentView().frame().size.height - (contentLayoutRect().origin.y + contentLayoutRect().size.height)` = 28 px logis. WebKit menggeser halaman turun sesuai safe area, tapi wry menaruh child webview di koordinat content view mentah. Dependency `objc2-app-kit` 0.3 khusus macOS; non-macOS mengembalikan 0.
- **Hide = suspend gratis** (terbukti dari source WebKit, belum diukur): `hide()` → `setHidden:` (view tetap di hierarchy) → WebKit membersihkan `ActivityState::IsVisible`, jadi rAF ter-suspend, animasi SVG pause, `visibilityState` `"hidden"`, `setTimeout`/`setInterval` ter-align ~1 Hz. Pane tersembunyi nyaris nol CPU, tapi chart berbasis rAF mati total sampai `show()`. Knob `BackgroundThrottlingPolicy` Tauri **tidak** mengatur kasus ini — ia hanya berlaku bagi webview yang *detached* dari view hierarchy.
- Selama pointer ditekan (drag splitter, menu terbuka, seret pane), frontend menyembunyikan semua webview lalu menampilkannya lagi (`createWebviewPointerSuppressor`, depth-counted), karena Tauri 2 hanya punya `setIgnoreCursorEvents` level window. Rust tidak punya logika drag — ia hanya menyediakan flag `visible`.
- `src/resize/resize.pointer-capture.ts` adalah registry suppressor; jangan tambah cabang if/else renderer di situ. Kelas `body.noc-resizing` implementasi iframe saja. Catat: `pane.webview-renderer.ts` mendaftarkan suppressor-nya sebagai efek samping saat modul diimpor.
- `src/pane/pane.renderer.ts` sengaja menerapkan `place`/`release`/`setCursorCapture` ke **kedua** renderer (no-op bagi yang tak melayani pane) agar layer geometri tak perlu tahu renderer mana yang dipakai.

**4. Handshake sidecar lewat stdout.** Rust men-spawn server dengan `NOC_PORT=0`, mem-parse baris `noc-ready <url>` untuk tahu port nyata, dan baru itu membuka window wall. Prefix terduplikasi sebagai literal di `src/server/server.ready.ts` dan `src-tauri/src/sidecar.rs` — **ubah keduanya bersama.** Server tidak pernah pindah port diam-diam: port terpakai = exit 1. Sidecar mengawasi `NOC_PARENT_PID` (signal 0, poll 1 s) agar tak jadi orphan; jangan andalkan parent membunuh child — force-quit tak pernah sampai ke kode itu.

**5. Permukaan frontend→native hanya 4 `invoke`:** `pane_webview_show|place|close` plus `cookie_import`, lewat `src/native/native.bridge.ts` saja. Tidak ada `emit`/`listen` dua arah — jangan tambahkan tanpa alasan kuat. Tiap command baru butuh **dua** entri: nama di `COMMANDS` (`src-tauri/build.rs`) yang membangkitkan permission `allow-*`, dan permission itu di `src-tauri/capabilities/default.json` — lupa yang pertama membuat build gagal dengan "Permission … not found" (wall page adalah origin remote `http://127.0.0.1:*`).

- **`pane_webview_show` tidak lagi selalu menavigasi, dan catatannya milik shell.** `PaneNavigations` (`Mutex<HashMap<label, url>>` di `pane_webview.rs`) menyimpan alamat terakhir yang dikirim ke tiap webview; `show` hanya menavigasi bila `navigate == Some(true)` **atau** alamatnya beda. Map itu wajib ada di Rust, bukan di halaman wall: halaman wall lupa segalanya tiap reload, sedangkan child webview-nya milik window dan hidup terus — itulah bug "pane balik ke halaman login tiap wall di-reload". Lock yang gagal diambil menjawab "belum sama" → tetap menavigasi (navigasi berlebih lebih murah daripada kehilangan alamat yang diminta user). **Jebakan bagi pemanggil: yang bermaksud *memuat ulang* alamat yang sama wajib mengirim `navigate: true`** — tanpa itu `show` diam-diam jadi no-op, tanpa error dan tanpa jejak. Hari ini pemanggil itu cuma satu: `open()` di `pane.webview-renderer.ts` menerima `navigate = false`, dan hanya `reopen` mengirim `true` (dipakai tombol Reload dan `reloadEveryPane` sesudah impor cookie). Pemanggil `show` berikutnya yang bermaksud memuat ulang harus ikut mengirimnya; yang hanya bermaksud *memindahkan* pane justru tak boleh — itulah seluruh alasan `PaneNavigations` ada. Test di `tests/pane/pane.webview-reload.test.tsx` menjaga sisi ini (gagal dengan `[undefined]` bila flag-nya dilepas); syarat di Rust-nya tak dijaga siapa pun.
- **`show` juga menerima `visible`, dan itu bukan duplikat `place`.** Satu pane memegang beberapa situs dan hanya satu tampil, sementara `show` dulu selalu memperlihatkan webview yang dibuat atau dinavigasinya — jadi tiap situs latar melukis di atas situs aktif sampai koreksi `place` datang satu putaran IPC kemudian, sekali per situs tiap wall di-reload. Sekarang `open()` di `pane.webview-renderer.ts` menghitung `onScreen(entry, rect)` (`visible && active && capturing && hasArea`) dan mengirimkannya; `visible` yang tak diisi tetap berarti "tampilkan". Di Rust, cabang webview baru memanggil `hide()` sesudah `add_child` — dan itu **bukan** menunda muat: view tetap di hierarchy, dokumennya tetap sampai, persis yang dibutuhkan situs yang dihangatkan di belakang saudaranya. Dijaga `tests/pane/pane.sites.test.tsx`; belum pernah dilihat di layar.
- `cookie_import` (`src-tauri/src/cookie_import.rs`) menanam cookie ekspor browser ke cookie store WebKit supaya pane tak minta login ulang. Ia **global, bukan per pane**: pane dibangun dengan `WebviewBuilder` polos — tanpa `incognito`, tanpa `data_store_identifier` — jadi semua berbagi `WKWebsiteDataStore::defaultDataStore`, dan webview window wall adalah pegangan yang sama atas store itu. Sekali impor berlaku untuk seluruh dinding.
- **Command ini membaca ulang store, dan itu bukan paranoia.** `Webview::set_cookie` fire-and-forget satu lapis di bawah: Tauri mengembalikan `Ok(())` begitu pesan masuk antrean, dan kalau WebKit menolak cookie-nya tauri-runtime-wry cuma menulis `log::error!`. Jadi yang dilaporkan adalah hasil `cookies()` sesudahnya (`stored`, `failedDomains`), bukan jumlah yang dikirim. Jangan "sederhanakan" jadi menghitung input.
- Command-nya `async` dengan sengaja: membaca cookie store memblokir sampai WebKit menjawab, dan Tauri mendokumentasikan itu deadlock bila dilakukan dari command sinkron di Windows. Input divalidasi (`usable`) karena `NSHTTPCookie::cookieWithProperties` mengembalikan nil untuk dictionary cacat dan wry mengubah nil itu jadi `expect` — panik yang menjatuhkan shell. `SameSite::None` di-drop wry di macOS; itu batas upstream, bukan bug di sini.
- Sisi web-nya **bukan** di `pane.store`: `src/session/session.store.ts` punya store zustand sendiri (parse → `nativeCookieBridge.importCookies` → `reloadEveryPane`) karena impor itu global untuk dinding, bukan milik satu pane. `session.store` boleh mengimpor `pane.store`; sebaliknya tidak pernah. **Reload sesudah impor bukan pemanis** — cookie yang ditanam tak berefek pada halaman yang sudah terlanjut dimuat, jadi tanpa itu fitur terlihat gagal total. `SessionCookie` (`session.types.ts`) satu-satunya deklarasi baris cookie; `native.bridge.ts` mengimpornya, jangan deklarasikan ulang.

**6. Pane iframe hanya bisa punya sesi bila situsnya same-site dengan dinding.** Cookie tanpa `SameSite` diperlakukan Chrome sebagai `Lax`, dan "site" dihitung dari dokumen **top-level** — jadi situs di domainnya sendiri menerima `Set-Cookie` lalu tak pernah mengirimnya kembali, dan halaman memantul ke login. Tak ada setting browser, Storage Access API, atau kode client yang bisa mengangkat itu. Maka dinding menyajikan tiap situs lewat reverse proxy di **subdomain host dinding sendiri** (`src/proxy/`): dinding di `wall.noc.localhost`, situs di `s-<nama>-<fingerprint>.noc.localhost`. Keduanya berbagi eTLD+1 `noc.localhost` (`localhost` tak ada di PSL, jadi label paling kanan jadi eTLD), dan itulah seluruh alasannya same-site. Yang terukur dan tak boleh ditebak ulang: `*.localhost` di kedalaman berapa pun resolve ke loopback tanpa `/etc/hosts` (RFC 6761 §6.3 — **janji Chrome**, jadi self-fetch sisi server tetap wajib ke `127.0.0.1`), **skema harus sama** antara dinding dan situs, dan cookie `Secure` tetap tersimpan di `http://*.localhost` karena origin itu potentially-trustworthy. Maka:

- **Empat hal di bawah ini adalah tanggung jawab proxy, dan masing-masing rusak senyap bila dihapus** (semua di `src/proxy/proxy.headers.ts` kecuali yang terakhir):
  - **`Domain` dibuang dari tiap `Set-Cookie` → keamanan, bukan beberes.** Sekarang semua situs bersaudara di bawah satu eTLD+1, cookie ber-`Domain=.noc.localhost` akan terbaca situs lain. Host-only cookie adalah satu-satunya yang memisahkan sesi situs A dari situs B. Dijaga test; jangan longgarkan.
  - **`Secure` dipertahankan.** Membuangnya justru satu-satunya cara merusak hal yang dibangun di sini — lihat fakta loopback di atas.
  - **`Location` ditulis ulang** ke label proxy yang sama. Login mana pun berakhir dengan redirect; redirect yang menunjuk origin asli melempar pane keluar dari jalur same-site dan bug-nya kembali persis seperti sebelum ada proxy. Redirect ke host **lain** sengaja dibiarkan apa adanya (SSO pihak ketiga tak dipasang user di dinding — lihat batas SSRF).
  - **`content-encoding` + `content-length` dibuang.** `fetch` Bun men-dekompresi gzip tapi meninggalkan kedua header itu utuh; meneruskannya membuat client men-dekode dua kali dan gagal dengan `ZlibError`.
  - **Antrean frame websocket** (`src/proxy/proxy.socket.ts`): browser mengirim frame pertamanya begitu socket-nya sendiri terbuka, saat socket upstream belum terhubung. Tanpa antrean frame itu hilang tanpa error dan tanpa close — dashboard tersambung lalu diam selamanya. Dashboard monitoring berat websocket, jadi ini bukan opsional.
- **Tetap loopback-only, dan proxy hanya mau ke origin yang memang dipasang user.** `src/proxy/proxy.registry.ts` adalah batas itu: label yang tak terdaftar dijawab 404 **tanpa fetch sama sekali**. Server ini sudah mem-fetch URL pilihan client lewat `/api/embeddability`; proxy memperbesar permukaan itu drastis, jadi jangan tambah opsi bind yang lebih luas dan jangan pernah mem-proxy host yang tak berasal dari situs di dinding.
- **Label situs harus stabil untuk situs yang sama**, karena dinding yang dimuat ulang dari layout tersimpan harus mendarat di hostname yang sama — hostname lain berarti cookie store lain, dan sesinya hilang justru pada saat yang mau diselamatkan. Maka label diturunkan dari origin situs itu sendiri (`siteLabel` di `src/proxy/proxy.label.ts`: nama terbaca + fingerprint FNV-1a, ≤63 karakter sesuai batas label DNS), bukan dari id pane, bukan dari counter, bukan dari `crypto.randomUUID()`.
- **URL yang dilihat & diedit user tetap URL aslinya.** `pane.iframe-renderer.tsx` memisahkan `pageUrl` (yang ditampilkan, dan yang dibawa event `frame-loaded` ke reducer load) dari `frameSrc` (yang dimuat). Reducer membuang event yang `url`-nya bukan yang dipegangnya, jadi mengirim URL proxy ke situ membuat pane menggantung di `loading` selamanya.
- **Jalur webview native tak lewat proxy sama sekali, dan memang tak perlu:** webview adalah dokumen top-level, jadi tak pernah cross-site terhadap siapa pun. Dinding yang dibuka di `127.0.0.1` (termasuk yang dimuat shell Tauri) juga mem-frame URL aslinya tanpa perubahan.
- **Browser tidak lagi disuruh pindah alamat — ia dipindahkan.** `catchAll` menjawab **307** ke `WALL_PROXY_HOSTNAME` (port, path, query dibawa utuh) saat `Host`-nya **hanya bisa berarti mesin ini**: `localhost`, `127.0.0.0/8`, `::1` (`wallLandingHostname` di `proxy.label.ts`). Sengaja lebih sempit daripada "bukan host proxy": dinding yang di-bind `0.0.0.0` dibaca browser orang lain, dan mengirimnya ke `*.localhost` berarti mengarahkannya ke mesinnya sendiri — dinding yang jalan jadi connection error. Anti-loop bukan daftar pengecualian melainkan sifat targetnya: `wall.noc.localhost` bukan nama loopback, jadi tak pernah memenuhi syarat pindah lagi; host situs `s-*` juga tidak, dan sudah keluar lebih dulu lewat `labelFor`. `/api/*` dan `WALL_SHELL_PATH` aman karena **route** Bun menang atas catch-all — 307 di atas PUT layout akan jadi jebakan. Banner pengarah (`ProxyHostNotice`) dihapus bersama perubahan ini: begitu pendaratannya otomatis, satu-satunya pembacanya adalah klien jarak jauh yang justru dituju salah olehnya.
- **Shell dikecualikan secara struktural, bukan lewat sniff user-agent:** `server.entry.ts` mengumumkan ready line lewat `stayOnHostUrl(...)`, yang menempelkan query `?stay=1` (`STAY_ON_HOST_PARAM` di `server.host-dispatch.ts`), dan `catchAll` menjawab di tempat bila flag itu ada. Dasarnya: alamat shell **dikonfigurasi server ini** (Rust cuma mem-parse `noc-ready <url>` lalu membukanya apa adanya — invariant 4), sedangkan alamat browser diketik manusia dan tak akan pernah membawanya. Nol perubahan di `src-tauri/`, dan bertahan melewati reload karena hidup di address bar. Flag biasa, bukan rahasia: pemakai keduanya adalah eksperimen kontrol cross-site repo ini sendiri (`cookie.demo-page.ts`), yang justru butuh dinding `127.0.0.1`. Pane chrome tak terpengaruh walau `chrome_url` di Rust menimpa query — `PANE_CHROME_PATH` route, bukan catch-all.
- Dispatch per-host ada di `src/server/server.host-dispatch.ts`: `Bun.serve` menyerahkan `Host` asli ke handler, jadi satu server menyajikan halaman dinding **dan** tiap subdomain situs. Rute API di-bungkus `wallOnly(...)` supaya situs tak pernah mewarisi `/api/*` dinding, dan halaman dinding diambil lewat self-fetch ke `WALL_SHELL_PATH` — bundler Bun merutekan per path, bukan per host. Format handshake `noc-ready` (invariant 4) tak disentuh — yang berubah hanya URL di belakang prefix, yang kini membawa `?stay=1`; Rust mem-parse-nya sebagai URL biasa, jadi nol perubahan di sana.

## Konvensi kode

- Nama file `[domain].[layer].ts(x)` tanpa kecuali; folder = domain. **Tanpa barrel `index.ts`, tanpa `utils/`, tanpa `helpers/`.**
- Impor dengan ekstensi file eksplisit (`./pane.store.ts`) — `allowImportingTsExtensions` + `verbatimModuleSyntax` aktif, jadi `import type` wajib untuk tipe.
- tsconfig strict penuh + `noUncheckedIndexedAccess` + `noFallthroughCasesInSwitch` + `noImplicitOverride`. TypeScript 7 (`^7.0.2`).
- Pisah tegas fungsi murni ↔ efek: `layout.tree`, `layout.remove`, `layout.move`, `resize.session`, `pane.load-state`, `pane.drag-geometry`, `embed.classifier`, `persist.snapshot` nol DOM/React/store. `pane.store.ts` hanya menyimpan state dan mengurutkan efek.
- Tiga store zustand, dan dua yang kecil bukan kelalaian: `pane.store` (state dinding, dipersistensi), `session.store` (impor cookie — global untuk dinding, bukan milik satu pane), `pane.drag` (`usePaneDragStore` — gerakan yang sedang berlangsung, nol persistensi, harus terbaca dari semua pane sekaligus agar tiap overlay tahu perannya). Arah impor satu arah ke `pane.store`, tak pernah sebaliknya — satu-satunya yang mengalir balik adalah tipe `DropZone` dari modul murni `pane.drag-geometry`, bukan dari store-nya. Commit tetap milik `pane.store` (`rearrangePane`).
- Pola port yang bisa di-inject: `createX(deps)` + singleton terpisah di file yang sama — `PaneRenderer`, `NativePaneBridge`, `WallPersistPort`, `PanePointerSuppressor`, `RectReader`, `GeometryRegistry`. Test membangun miliknya sendiri; jangan mem-mock modul.
- Error memakai result-type (`{ok:true,...} | {ok:false, reason}`) bukan throw; throw hanya untuk input user/operator yang salah (`readConfig`, `splitPane` pada pane docked).
- Tiap file dibuka docblock **"kenapa"**, bukan "apa". Pertahankan pola itu — komentar-komentar itulah yang mencegah invariant di atas "dibetulkan".
- `data-testid` di tiap elemen penting: `slot-`, `split-`, `splitter-`, `pane-frame-`, `pane-host-`, `pane-webview-`, `pane-empty-`, `pane-refused-`, `pane-cookie-warning-`, `pane-chrome-`, `pane-menu-button-`, `pane-menu-`, `pane-strategy-`, `pane-reload-`, `pane-split-row-`/`pane-split-column-`, `pane-close-`, `pane-import-cookies-` (+ `-input-`/`-status-`), `pane-drop-` (overlay seret; peran & zona dibaca dari atribut `data-drop-role` = `source`/`target`/`idle` dan `data-drop-zone`, bukan dari kelas CSS), plus switcher situs: `pane-site-switcher-`, `pane-site-<siteId>` (satu pip), `pane-site-toggle-` (chip hitungan), `pane-site-row-`/`pane-site-remove-` (daftar di panel), `pane-site-add-`.
- **`pane-frame-`/`pane-webview-` bercabang pada aktif/tidak** lewat `paneContentTestId` (`pane.renderer.ts`): situs aktif tetap `pane-frame-<paneId>` persis seperti sebelum pane memegang banyak situs, situs latar jadi `pane-frame-<paneId>-<siteId>`. Itu disengaja supaya test lama tak perlu tahu soal situs; jangan seragamkan jadi selalu bersuffix.
- Satu-satunya hook DOM non-testid yang dipakai logika runtime: `data-pane-slot` (geometri) dan `data-pane-host` (hit-test target drop di `pane.drag.ts`). Keduanya kontrak, bukan sisa debug.

## Env & keamanan

Semua env dibaca **hanya** di `src/config/config.env.ts` — jangan baca `process.env` di tempat lain. `NOC_HOST` (127.0.0.1) · `NOC_PORT` (7788, `0` = ephemeral) · `NOC_DATA_DIR` (.noc-data) · `NOC_DB_FILE` (noc.sqlite) · `NOC_LOG_LEVEL` (info — divalidasi tapi belum dipakai di mana pun) · `NOC_PARENT_PID`. Shell Rust meneruskan `NOC_HOST`, `NOC_PORT`, `NOC_PARENT_PID`, plus `NOC_DB_FILE`/`NOC_LOG_LEVEL` bila di-set (`sidecar_env()` di `src-tauri/src/sidecar.rs`).

**`NOC_DATA_DIR` bukan sekadar diteruskan — shell mengisinya bila operator tidak memilih**, dengan `app.path().app_data_dir()` (`~/Library/Application Support/dev.noc.wall` di macOS), dan `create_dir_all` dijalankan sebelum sidecar di-spawn. Alasannya: default `.noc-data` itu **relatif**, dan `.app` di-launch OS dengan cwd `/`, yang diwarisi sidecar — jadi databasenya jatuh ke `/.noc-data/noc.sqlite` di volume read-only dan seluruh dinding jalan tanpa bisa menyimpan apa pun. Default relatif itu tetap benar untuk `bun run dev`/`start` (cwd = project, dan `rm -rf .noc-data` = reset), jadi `config.env.ts` tidak diubah; yang salah bukan defaultnya, tapi shell yang membiarkan proses ber-cwd tak terduga memakainya. Konsekuensi yang disengaja: `tauri:dev` dan bundle sekarang memakai direktori data yang **sama**, jadi yang diuji sama dengan yang dirilis. Nilai operator selalu menang, dan nilai kosong dihitung sebagai "tak di-set" (persis seperti `||` di `config.env.ts`) supaya `NOC_DATA_DIR=""` tak diam-diam mengembalikan jebakan ini. Kegagalan resolve/mkdir di-`eprintln` lalu path-nya tetap dikirim: sidecar mencoba lagi dan, bila gagal juga, pesan di pita merah menyebut direktori yang masuk akal, bukan `/.noc-data`.

Loopback bukan kebetulan: `/api/embeddability` membuat server mem-fetch URL pilihan client (SSRF bila terbuka) dan layout tersimpan berisi nama dashboard internal. Bind ke `0.0.0.0` hanya atas permintaan eksplisit operator. Path database di-resolve terhadap base dir eksplisit, bukan `process.cwd()`, dan tidak boleh berada di dalam executable (`bun build --compile` menerima tulisan lalu membuangnya saat proses keluar).

Jadi satu-satunya cara menilainya adalah `bun run tauri:build` lalu menjalankan `.app`-nya; `tauri:dev` akan tetap gagal dan itu bukan bukti apa-apa. Belum terbukti juga: apakah macOS benar-benar memunculkan prompt, dan bagaimana prompt itu terlihat di atas webview yang melukis di level OS.
- **Setiap pane boleh minta kamera, tanpa pandang bulu, dan di shell native tanpa bertanya.** Itu keputusan sadar, bukan kelalaian: `allow` wall-wide karena membuatnya per-pane berarti field baru di node pane — perubahan schema, bukan toggle. Di browser pengguna masih dapat prompt; di shell native wry menjawab `Grant` tanpa handler, jadi tidak. Knob-nya `tauri::Builder::on_permission_request` di `main.rs` (lihat docblock `pane_webview.rs`) — jangan pasang sebelum ada yang memastikan WKWebView benar-benar menampilkan prompt untuk `Prompt`, karena tebakan yang salah menukar grant diam-diam dengan deny diam-diam.
- **Switcher situs (pip / chip `3/8`) ada, ter-unit-test, nol bukti visual.** Angkanya aritmetika terhadap stylesheet yang tak dimuat test mana pun, di DOM yang mengukur semua nol: pip 8 px + gap 4 px → baris `12n − 4` px, sementara pane tersempit ~96 px (`MIN_FRACTION` 0.05 dari 1920) dan ⋮ harus muat di sebelahnya. `MAX_INLINE_SITE_PIPS` = 4 adalah tebakan di mana pip berhenti jadi target yang bisa dikenai pointer — bukan hasil pengukuran. Detail yang bisa dilihat ada di README "Open items"; yang penting di sini: jangan ubah angka itu sambil mengira ada yang pernah memverifikasinya.
- **Perbaikan navigasi (`PaneNavigations`) belum pernah dijalankan.** Yang ter-test hanya kontrak sisi web — `reopen` mengirim `navigate: true`, sebuah pemindahan tidak — dan syarat yang memutuskannya hidup di Rust, yang tak di-test sama sekali. Jadi belum terbukti dua-duanya: bahwa pane benar-benar bertahan di halamannya saat halaman wall di-reload, dan bahwa Reload benar-benar mengambil ulang halaman alih-alih diam. Hanya bisa dinilai dengan Cmd-R di halaman wall sungguhan; lihat README "Open items".
- **Peringatan cookie pane iframe diam pada kasus yang paling sering.** `embed.cookies.ts` menilai `Set-Cookie` dari respons probe yang **sudah** ada di tangan — nol fetch tambahan — dan `pane.cookie-notice.tsx` menyebut nama cookie yang tak akan terkirim. Tapi probe itu satu `GET` ke URL pane, dan halaman login umumnya **tidak** men-set cookie apa pun di GET: cookie sesi lahir di `POST` login, yang tak pernah dilihat server ini. Verdict `unknown` → baris tak muncul, dan itu disengaja (nol bukti = diam, bukan tebakan). Artinya untuk kasus pemicunya sendiri (dashboard yang login lalu memantul) peringatan ini **mungkin tidak pernah tampil**; yang tertangkap adalah situs yang men-set cookie di muatan pertama. Nol bukti visual juga: tinggi/kontras baris di atas dashboard terang & gelap, dan apakah `align-self: end` benar-benar tak menutupi apa pun yang berguna, belum pernah dilihat di layar. **Dan sejak proxy mendarat, baris ini diam di seluruh jalur proxy dengan sengaja** — `createEmbeddabilityHandler` menjawab lebih awal tanpa field `cookies` ketika situsnya didaftarkan ke proxy, karena di sana cookie yang diperingatkan justru terkirim. Yang tersisa sebagai pemakainya: dinding yang dibuka langsung di `127.0.0.1:7788`, yang juga jalur Tauri.
- **Proxy same-site: sesi terbukti bertahan di Chrome sungguhan, tapi hanya terhadap situs tiruan.** Yang sudah dilihat di layar (Chrome 155, profil sementara, perbandingan tiga arah): cookie sesi kembali di dalam pane dan bertahan melewati reload halaman dinding, kontrol di `127.0.0.1` memantul ke login seperti dulu, situs ber-`X-Frame-Options: SAMEORIGIN` + `frame-ancestors 'none'` ter-frame dan bisa login, dan dua cookie host-only terpisah per label di cookie store Chrome. Yang **belum** terbukti dan diketahui bisa pecah: tak satu pun dashboard sungguhan pernah lewat jalur ini — hanya situs tiruan; **URL absolut di dalam konten** (halaman yang menyusun link/XHR dari origin aslinya, bukan dari `location`) keluar dari jalur same-site dan tak ada yang menulis ulang body; situs yang **memvalidasi `Origin`/`Referer` ketat** bisa menolak dengan galat CSRF yang terlihat persis seperti bug login yang disembuhkan di sini; **websocket terautentikasi** hanya terbukti sejauh demo echo; **service worker** (scope per origin, jadi terdaftar di bawah label proxy) belum disentuh sama sekali; dan redirect SSO ke host pihak ketiga sengaja tak ditulis ulang, jadi login yang memantul ke penyedia luar akan keluar dari proxy di tengah jalan.
