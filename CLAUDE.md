# CLAUDE.md — NOC wall

Dinding pane berpetak; tiap pane memegang satu atau beberapa situs (semuanya ter-mount, satu aktif). Bun (server + bundler + test runner + compiler) · React 19 · react-router 8 **library mode** · zustand 5 · SQLite via `bun:sqlite`. **Web saja** — satu renderer (iframe), dikirim sebagai PWA atau sebagai satu file executable. v0.4.0.
README = produk & milestone untuk manusia. File ini = perintah, invariant, jebakan. Jangan saling duplikasi.

**Shell desktop Tauri sudah dihapus seluruhnya** (commit `8a6c016`), bukan dipensiunkan: nol `src-tauri/`, nol `src/native/`, nol `@tauri-apps/*`, nol renderer webview native. Alasannya ada di invariant 2 — webview native hanya mengerjakan dua hal (situs yang menolak di-frame, dan sesi login di dalam pane) dan proxy same-site mengerjakan keduanya tanpa shell. **Satu hal benar-benar hilang bersamanya: impor cookie** (`cookie_import` menulis ke `WKWebsiteDataStore`, tak ada padanannya di browser). Penggantinya kalau suatu saat dibutuhkan adalah injeksi cookie di sisi proxy — fitur baru dengan argumen keamanannya sendiri, bukan porting. Jangan hidupkan kembali potongan Tauri mana pun; git punya sejarahnya.

## Perintah

- `bun install` · `bun run dev` (hot, http://127.0.0.1:7788) · `bun run start` (tanpa hot)
- `bun test` (41 file `*.test.ts(x)` di `tests/`) · `bun run typecheck` (`tsc --noEmit`)
- `bun run build:binary` → `dist/noc`, satu file untuk host ini
- `bun run build:binary:all` → enam target silang (`scripts/binary.build.ts`); hanya binary host yang pernah dijalankan

`src/server/server.entry.ts` satu-satunya entrypoint server — `bun run dev`, `bun run start`, dan binary terkompilasi memakai file yang sama. `import index from "../../index.html"` itulah yang membuat frontend ikut masuk ke dalam executable; tidak ada jalur penyajian aset kedua yang harus dijaga sinkron.

`src/app/app.css` satu-satunya stylesheet yang di-link halaman — sejak dipecah ia pengimpor tiga layer, bukan lagi tempat rule; semua kelas ber-prefix `noc-`.

**`app.css` sudah dipecah — pengecualian 500 baris itu habis pada 710 baris / 19.977 karakter (sisa 23 karakter dari batas keras 20.000).** Yang dipertahankan bukan "satu file", melainkan hal yang membuat satu file itu berharga: tepat satu jawaban atas "rule mana yang menang". Maka `app.css` **tinggal pengimpor** — tiga `@import` dan nol rule — dan urutannya bagian dari kontrak, bukan abjad:

1. `app.base.css` — token `--noc-*` di `:root`, reset, aturan dokumen (`overflow`/`overscroll-behavior`), pita notice, kontrol fullscreen, lalu seluruh pohon layout: shell, split, slot kosong, splitter, plus pasangan `body.noc-resizing`. **Wajib pertama**: dua layer di bawahnya membaca custom property yang didefinisikan di sini.

## Invariant yang tidak boleh dilanggar

**1. Iframe tidak boleh berganti parent DOM.** Ganti parent = React bikin node baru = halaman reload. Maka:

- `src/layout/layout.renderer.tsx` merender pohon sebagai flex bersarang yang daunnya **div kosong** ber-`data-pane-slot`. Div kosong itu BUKAN bug — menaruh konten di situ mengikat DOM pane ke bentuk pohon.
- Pane hidup di satu flat list di `src/pane/pane.layer.tsx`, urutannya selalu creation order (`createdAt`, tie-break `id`) dan tidak pernah berubah. Jangan pindahkan pane ke dalam pohon layout, jangan urutkan ulang list ini.
- `src/geometry/geometry.sync.ts` menyalin rect slot ke host pane secara imperatif (`useLayoutEffect` + `ResizeObserver` di `src/app/app.shell.tsx`), memakai `transform: translate(...)` (`geometry.rect.ts:rectToStyle`), bukan `left`/`top`. Jangan posisikan pane lewat state React.
- `splitPane` (`src/layout/layout.tree.ts`) **wajib** mempertahankan id pane asal; hanya split node + pane baru yang dapat id baru.
- Hal yang sama berlaku untuk `movePane`/`swapPanes` (`src/layout/layout.move.ts`) — itulah satu-satunya alasan seret pane tidak me-reload halaman. `movePane` memang mencetak id **split** baru lewat `makeId`, tapi tak pernah id pane; guard `pane.parentId === null` ada supaya `detachLeaf` tak pernah mencapai cabang reseed-nya (cabang itu mencetak pane baru). `swapPanes` tak butuh `makeId` sama sekali: ia hanya menukar slot anak + `parentId`, bentuk pohon dan `sizes` tetap utuh.
- `rearrangePane` di `pane.store.ts` melakukan satu `set` untuk seluruh perpindahan. Detach lalu insert dalam dua commit menyisakan satu frame di mana pane tak punya slot, dan pane tanpa slot disembunyikan. Penolakan (`pane-docked`, `pane-not-in-tree`) meninggalkan dinding apa adanya.
- Pane tanpa slot disembunyikan (`visibility: hidden`), bukan diberi rect nol — viewport nol membuat halaman reflow dan kehilangan scroll.
- `useShallow` di `usePaneIdsInCreationOrder` wajib; tanpa itu seluruh pane layer re-render tiap perubahan store.
- **Satu pane memegang daftar situs, dan semuanya ter-mount sekaligus** di satu grid cell `.noc-pane__body` (`grid-template-areas: "stack"`), satu `renderer.Content` per situs ber-`key={site.id}`. Yang tidak aktif **disembunyikan** lewat `noc-pane__frame--hidden` (`visibility`), bukan di-unmount. Berpindah situs = satu tulisan tree (`setActiveSite`) — alasan yang sama dengan pane tanpa slot: rect nol atau unmount berarti reload, scroll hilang, sesi hilang.
- **`state.load` dikunci per `siteId`, bukan per pane:** status muat milik halaman, bukan milik pane. Selector `paneLoadState`/`siteLoadState` ada di `pane.store-sites.ts`, bukan di `pane.store.ts`.
- **Zoom juga per situs, dan ia CSS `zoom` di elemen `<iframe>` itu sendiri — bukan `transform`, bukan elemen pembungkus, bukan host.** Ketiganya adalah satu invariant yang sama dilihat dari tiga sisi: pembungkus baru berarti iframe berganti parent (halaman reload — seluruh isi invariant 1), dan host sudah memegang `transform: translate(...)` tulisan `geometry.sync.ts`. Yang tersisa cuma properti di elemen iframe-nya. Antara `zoom` dan `transform: scale()` keduanya **terukur sama** di Chrome 155 — sama-sama memperbesar, sama-sama hit-test benar (klik di (150,150) pada host mendarat di sel yang sama untuk keduanya, dan bukan sel yang sama dengan kontrol tanpa zoom) — jadi pemenangnya ditentukan harga: `zoom` satu properti, `transform` butuh tiga yang harus tetap sinkron (`scale` + `transform-origin: top left` + `width`/`height: calc(100% / k)`) dan diam-diam menggeser viewport bila salah satunya melenceng, plus ia menjadikan iframe containing block + stacking context di dalam host yang sudah menumpuk chrome mengambang terhadapnya. Tangga rung-nya milik Chrome (`src/layout/layout.zoom.ts`, murni): kedua ujung berhenti keras dan tombolnya di-`disabled`, tidak diam-diam no-op. `clampZoom` menerima `unknown` karena layout tersimpan dan file SQLite di disk operator sama-sama tak tepercaya — zoom 0 atau 40 adalah halaman tanpa jalan kembali.

**2. Penolakan framing tidak bisa dideteksi dari client.** Iframe terblokir `X-Frame-Options` tetap memicu `load` di Chromium dan dokumennya tak terbaca. Maka:

- Klasifikasi server-side: `GET /api/embeddability?url=` → `src/server/embed.probe.ts` (fetch target, `body.cancel()`, timeout 8 s) → `src/embed/embed.classifier.ts` (`X-Frame-Options` + CSP `frame-ancestors`). Di jalur **langsung** (pane menunjuk origin aslinya) tetap tak ada satu pun header target yang di-strip atau ditulis ulang — penolakan dilaporkan ke user, bukan diakali.
- **Di jalur proxy, bagian "tidak ada header yang ditulis ulang" dicabut — sadar, atas perintah eksplisit, dan bukan demi mengakali penolakan framing.** Sebabnya ada di invariant 3: cookie sesi tak pernah kembali ke iframe cross-site, dan satu-satunya jalan dalam app adalah membuat situs **same-site** dengan halaman dinding. Begitu trafiknya lewat host dinding, `X-Frame-Options` toh tak bisa lagi menolak apa pun — dinding *adalah* originnya. Jadi hilangnya penolakan framing adalah efek samping yang diterima, bukan tujuan. Konsekuensi yang harus jujur: `/api/embeddability` menjawab `verdict: "unknown"` untuk situs yang akan di-frame lewat host dinding (`createEmbeddabilityHandler` di `server.routes.ts`) — menjawab `refused` di situ akan jadi bohong. Daftar lengkap header yang disentuh beserta alasan per baris ada di `src/proxy/proxy.headers.ts`; jangan tambah entri tanpa alasan tertulis di situ juga.
- **Riset independen menegaskan tak ada jalan lain:** tak satu pun browser menyediakan cara client-side membatalkan `X-Frame-Options`/`frame-ancestors`. Proxy same-site bukan workaround sementara, ia **satu-satunya** mekanisme yang app ini punya — itulah kenapa menghapus renderer webview native bukan pemangkasan fitur.
- State pane = reducer murni `src/pane/pane.load-state.ts`: `empty → probing → loading | refused → ready`. Tiap event membawa `url`-nya agar hasil probe untuk alamat lama dibuang. Jangan menambah pembacaan `iframe.contentDocument` atau timer "kalau belum load berarti ditolak".
- Verdict `unknown` sengaja optimistis → `loading`; `probe-failed` juga.

**3. Pane hanya bisa punya sesi bila situsnya same-site dengan dinding.** Cookie tanpa `SameSite` diperlakukan Chrome sebagai `Lax`, dan "site" dihitung dari dokumen **top-level** — jadi situs di domainnya sendiri menerima `Set-Cookie` lalu tak pernah mengirimnya kembali, dan halaman memantul ke login. Tak ada setting browser, Storage Access API, atau kode client yang bisa mengangkat itu. Maka dinding menyajikan tiap situs lewat reverse proxy di **subdomain host dinding sendiri** (`src/proxy/`): dinding di `wall.noc.localhost`, situs di `s-<nama>-<fingerprint>.noc.localhost`. Keduanya berbagi eTLD+1 `noc.localhost` (`localhost` tak ada di PSL, jadi label paling kanan jadi eTLD), dan itulah seluruh alasannya same-site. Yang terukur dan tak boleh ditebak ulang: `*.localhost` di kedalaman berapa pun resolve ke loopback tanpa `/etc/hosts` (RFC 6761 §6.3 — **janji Chrome**, jadi self-fetch sisi server tetap wajib ke `127.0.0.1`), **skema harus sama** antara dinding dan situs, dan cookie `Secure` tetap tersimpan di `http://*.localhost` karena origin itu potentially-trustworthy. Maka:

- **Lima hal di bawah ini adalah tanggung jawab proxy, dan masing-masing rusak senyap bila dihapus** (semua di `src/proxy/proxy.headers.ts` kecuali yang terakhir):
  - **`Domain` dibuang dari tiap `Set-Cookie` → keamanan, bukan beberes.** Sekarang semua situs bersaudara di bawah satu eTLD+1, cookie ber-`Domain=.noc.localhost` akan terbaca situs lain. Host-only cookie adalah satu-satunya yang memisahkan sesi situs A dari situs B. Dijaga test; jangan longgarkan.
  - **`Secure` dipertahankan.** Membuangnya justru satu-satunya cara merusak hal yang dibangun di sini — lihat fakta loopback di atas.
  - **`Location` ditulis ulang** ke label proxy yang sama. Login mana pun berakhir dengan redirect; redirect yang menunjuk origin asli melempar pane keluar dari jalur same-site dan bug-nya kembali persis seperti sebelum ada proxy. Redirect ke host **lain** sengaja dibiarkan apa adanya (SSO pihak ketiga tak dipasang user di dinding — lihat batas SSRF).
  - **`content-encoding` + `content-length` dibuang.** `fetch` Bun men-dekompresi gzip tapi meninggalkan kedua header itu utuh; meneruskannya membuat client men-dekode dua kali dan gagal dengan `ZlibError`.
  - **`camera`/`microphone` dibuang dari `Permissions-Policy` situs** (dan dari `Feature-Policy` lama), directive lain utuh. Situs boleh memveto kamera untuk dirinya sendiri dan delegasi container tak bisa membatalkan itu; ini satu-satunya tempat veto itu bisa dicabut.
  - **Antrean frame websocket** (`src/proxy/proxy.socket.ts`): browser mengirim frame pertamanya begitu socket-nya sendiri terbuka, saat socket upstream belum terhubung. Tanpa antrean frame itu hilang tanpa error dan tanpa close — dashboard tersambung lalu diam selamanya. Dashboard monitoring berat websocket, jadi ini bukan opsional.
- **Tetap loopback-only, dan proxy hanya mau ke origin yang memang dipasang user.** `src/proxy/proxy.registry.ts` adalah batas itu: label yang tak terdaftar dijawab 404 **tanpa fetch sama sekali**. Server ini sudah mem-fetch URL pilihan client lewat `/api/embeddability`; proxy memperbesar permukaan itu drastis, jadi jangan tambah opsi bind yang lebih luas dan jangan pernah mem-proxy host yang tak berasal dari situs di dinding.
- **Label situs harus stabil untuk situs yang sama**, karena dinding yang dimuat ulang dari layout tersimpan harus mendarat di hostname yang sama — hostname lain berarti cookie store lain, dan sesinya hilang justru pada saat yang mau diselamatkan. Maka label diturunkan dari origin situs itu sendiri (`siteLabel` di `src/proxy/proxy.label.ts`: nama terbaca + fingerprint FNV-1a, ≤63 karakter sesuai batas label DNS), bukan dari id pane, bukan dari counter, bukan dari `crypto.randomUUID()`.
- **URL yang dilihat & diedit user tetap URL aslinya.** `pane.iframe-renderer.tsx` memisahkan `pageUrl` (yang ditampilkan, dan yang dibawa event `frame-loaded` ke reducer load) dari `frameSrc` (yang dimuat). Reducer membuang event yang `url`-nya bukan yang dipegangnya, jadi mengirim URL proxy ke situ membuat pane menggantung di `loading` selamanya.
- **Browser tidak disuruh pindah alamat — ia dipindahkan.** `catchAll` menjawab **307** ke `WALL_PROXY_HOSTNAME` (port, path, query dibawa utuh) saat `Host`-nya **hanya bisa berarti mesin ini**: `localhost`, `127.0.0.0/8`, `::1` (`wallLandingHostname` di `proxy.label.ts`). Sengaja lebih sempit daripada "bukan host proxy": dinding yang di-bind `0.0.0.0` dibaca browser orang lain, dan mengirimnya ke `*.localhost` berarti mengarahkannya ke mesinnya sendiri — dinding yang jalan jadi connection error. Anti-loop bukan daftar pengecualian melainkan sifat targetnya: `wall.noc.localhost` bukan nama loopback, jadi tak pernah memenuhi syarat pindah lagi; host situs `s-*` juga tidak, dan sudah keluar lebih dulu lewat `labelFor`. `/api/*`, `/pwa/*` dan `WALL_SHELL_PATH` aman karena **route** Bun menang atas catch-all — 307 di atas PUT layout akan jadi jebakan.
- **`?stay=1` masih hidup sebagai konsumen tanpa produsen, dan itu disengaja.** `STAY_ON_HOST_PARAM` (`server.host-dispatch.ts`) membuat `catchAll` menjawab di tempat alih-alih memindahkan. Produsennya dulu ready line shell Tauri (`stayOnHostUrl`), yang ikut terhapus; grep `src/` sekarang nol produsen. Pemakai yang tersisa adalah manusia dan eksperimen kontrol cross-site repo ini sendiri (`cookie.demo-page.ts`), yang justru butuh dinding di `127.0.0.1` untuk membuktikan bug-nya masih ada di luar proxy. **Jangan hapus flag itu sebagai "dead code"** — ia satu-satunya cara mencapai dinding tanpa proxy, dan tanpanya kontrol negatif repo ini tak bisa dijalankan.
- Dispatch per-host ada di `src/server/server.host-dispatch.ts`: `Bun.serve` menyerahkan `Host` asli ke handler, jadi satu server menyajikan halaman dinding **dan** tiap subdomain situs. Rute API di-bungkus `wallOnly(...)` supaya situs tak pernah mewarisi `/api/*` maupun `/pwa/*` dinding, dan halaman dinding diambil lewat self-fetch ke `WALL_SHELL_PATH` — bundler Bun merutekan per path, bukan per host.

**4. Dinding dikirim sebagai satu file, dan dua hal di dalamnya mudah dirusak tanpa sadar.**

- **Tag PWA tidak bisa tinggal di `index.html`, dan tak akan pernah bisa.** Bundler HTML Bun me-resolve tiap `href` pada waktu build: path absolut yang dijawab route (`/pwa/manifest.webmanifest`) adalah **build error**, dan path relatif ke file sungguhan ditulis ulang jadi URL ber-hash yang `icons[].src` di manifest takkan pernah cocoki. Maka ketiga tag (`<link rel="manifest">`, `<meta name="theme-color">`, `<link rel="apple-touch-icon">`) ditempelkan di `withPwaHead` (`src/pwa/pwa.head.ts`), fungsi string murni yang dipanggil di satu chokepoint yang sudah dilewati tiap alamat dinding menghadap-browser. **Bukan `HTMLRewriter`** — ia menolak `Response` happy-dom, jadi file-nya akan jadi tak bisa di-test. Body yang membesar wajib membuang `content-length` + `content-encoding`, bahaya yang sama dengan `proxy.headers.ts`.
- **Tak ada service worker, dan itu keputusan, bukan kelalaian.** Chrome berhenti mensyaratkan fetch handler untuk installability sejak 112, dan di sini tak ada pekerjaan untuknya: tiap pane adalah iframe hidup di origin lain yang worker ber-origin dinding tak bisa lihat maupun cache, sementara shell ter-cache akan hidup lebih lama daripada binary yang menyajikannya — dinding yang dikompilasi ulang mengirim aset ber-hash baru ke client yang masih memegang yang lama. Chrome menyediakan halaman offline-nya sendiri. Yang ditambahkan sebuah worker cuma basi.
- **Ikon di-`import … with { type: "file" }` lalu disajikan lewat `Bun.file`**, jadi dua baris yang sama bekerja dari source maupun dari dalam binary. `pwaIconFiles` diekspor khusus sebagai penjaga kabel-mati: ia yang membuat test gagal kalau rutenya tak lagi menunjuk file yang di-import.
- **Direktori data tak boleh relatif di binary.** `.noc-data` benar untuk `bun run dev`/`start` (cwd = project, `rm -rf .noc-data` = reset) tapi jebakan untuk executable terdistribusi, yang bisa di-launch OS dengan cwd `/` atau di mount read-only — jebakan ini sudah pernah menelan korban sekali (bundle `.app` berjalan dengan database di `/.noc-data/noc.sqlite`, tak bisa menyimpan apa pun). `defaultDataDir` di `config.env.ts` memilih direktori per-user begitu `Bun.isStandaloneExecutable` benar. Lihat bagian "Env & keamanan".
- **`--bytecode` mati dan tetap mati**: kunci-nya hash JSC jadi ia fallback diam-diam antar versi Bun, ada bug ESM terbuka, dan yang dibelinya cuma waktu start proses untuk server yang distart sekali. `--minify` dan `--sourcemap` hidup, supaya stack trace binary yang sudah dipindah tetap menyebut file `.ts` dan barisnya.

**5. Fullscreen di monitor bernama adalah pengganti window shell, bukan tambahan di sebelahnya.** `src/display/` memakai Window Management API: izin di-probe saat mount, tapi layarnya **tidak** — mengenumerasi layar memunculkan prompt, dan tak boleh ada `await` sebelum panggilan fullscreen atau prompt itu memakan user activation. Tanpa API-nya kontrol jatuh ke `requestFullscreen()` polos tanpa cabang, karena browser yang tak mengenal dictionary screen mengabaikannya. `screenAccess()` menjawab `"unavailable"` saat API-nya absen — jangan ubah jadi throw; happy-dom punya `getScreenDetails` (satu layar primer tanpa nama) tapi tak punya `requestFullscreen`.

## Konvensi kode

- Nama file `[domain].[layer].ts(x)` tanpa kecuali; folder = domain. **Tanpa barrel `index.ts`, tanpa `utils/`, tanpa `helpers/`.**
- Impor dengan ekstensi file eksplisit (`./pane.store.ts`) — `allowImportingTsExtensions` + `verbatimModuleSyntax` aktif, jadi `import type` wajib untuk tipe.
- tsconfig strict penuh + `noUncheckedIndexedAccess` + `noFallthroughCasesInSwitch` + `noImplicitOverride`. TypeScript 7 (`^7.0.2`).
- Pisah tegas fungsi murni ↔ efek: `layout.tree`, `layout.remove`, `layout.move`, `layout.zoom`, `resize.session`, `pane.load-state`, `pane.drag-geometry`, `embed.classifier`, `persist.snapshot`, `proxy.label`, `proxy.headers`, `pwa.head` nol DOM/React/store. `pane.store.ts` hanya menyimpan state dan mengurutkan efek.
- Dua store zustand, dan yang kecil bukan kelalaian: `pane.store` (state dinding, dipersistensi) dan `pane.drag` (`usePaneDragStore` — gerakan yang sedang berlangsung, nol persistensi, harus terbaca dari semua pane sekaligus agar tiap overlay tahu perannya). Arah impor satu arah ke `pane.store`, tak pernah sebaliknya — satu-satunya yang mengalir balik adalah tipe `DropZone` dari modul murni `pane.drag-geometry`, bukan dari store-nya. Commit tetap milik `pane.store` (`rearrangePane`).
- Pola port yang bisa di-inject: `createX(deps)` + singleton terpisah di file yang sama — `PaneRenderer`, `WallPersistPort`, `PanePointerSuppressor`, `RectReader`, `GeometryRegistry`. Test membangun miliknya sendiri; jangan mem-mock modul.
- Error memakai result-type (`{ok:true,...} | {ok:false, reason}`) bukan throw; throw hanya untuk input user/operator yang salah (`readConfig`, `splitPane` pada pane docked).
- Tiap file dibuka docblock **"kenapa"**, bukan "apa". Pertahankan pola itu — komentar-komentar itulah yang mencegah invariant di atas "dibetulkan".
- `data-testid` di tiap elemen penting: `slot-`, `split-`, `splitter-`, `pane-frame-`, `pane-host-`, `pane-empty-`, `pane-refused-`, `pane-cookie-warning-`, `pane-chrome-`, `pane-menu-button-`, `pane-menu-`, `pane-reload-`, `pane-split-row-`/`pane-split-column-`, `pane-close-`, `pane-drop-` (overlay seret; peran & zona dibaca dari atribut `data-drop-role` = `source`/`target`/`idle` dan `data-drop-zone`, bukan dari kelas CSS), switcher situs `pane-site-switcher-`, `pane-site-<siteId>` (satu pip), `pane-site-toggle-` (chip hitungan), `pane-site-row-`/`pane-site-remove-` (daftar di panel), `pane-site-add-`, zoom `pane-zoom-out-`, `pane-zoom-level-` (angka persen, sekaligus tombol reset), `pane-zoom-in-`, plus fullscreen `wall-fullscreen`, `wall-fullscreen-find`, `wall-fullscreen-problem`, `wall-fullscreen-toggle`, `wall-fullscreen-screen-<id>`.
- **`pane-frame-` bercabang pada aktif/tidak** lewat `paneContentTestId` (`pane.renderer.ts`): situs aktif tetap `pane-frame-<paneId>` persis seperti sebelum pane memegang banyak situs, situs latar jadi `pane-frame-<paneId>-<siteId>`. Itu disengaja supaya test lama tak perlu tahu soal situs; jangan seragamkan jadi selalu bersuffix.
- `src/pane/pane.renderer.ts` tinggal 61 baris: tipe props + penamaan testid. Dengan satu renderer tak ada lagi yang perlu dipilih, tak ada yang di luar DOM untuk di-`place` manual, dan tak ada yang perlu dihancurkan yang tidak ikut terbawa React saat elemennya hilang. **Jangan hidupkan kembali interface renderer** untuk satu implementasi.
- `src/resize/resize.pointer-capture.ts` tetap registry walau implementasinya tinggal satu (`iframePanePointerSuppressor`, mendaftar sebagai efek samping saat modul diimpor). Tiga pemanggil berbagi konsepnya — drag splitter, panel ⋮, dan seret pane — dan yang mereka inginkan adalah konsepnya, bukan kelasnya. Jangan tambah cabang if/else renderer di situ.
- Satu-satunya hook DOM non-testid yang dipakai logika runtime: `data-pane-slot` (geometri) dan `data-pane-host` (hit-test target drop di `pane.drag.ts`). Keduanya kontrak, bukan sisa debug.

## Chrome pane, menu, dan seret

- **Chrome permanen pane = satu kotak mengambang (⋮ + pip situs).** `.noc-pane__chrome` — `position: absolute`, pojok kanan atas, **nol tinggi terpakai**. Label host hidup sebagai `title` tombol, nol piksel. **Sejarah supaya tidak diputar ulang:** bentuk ini menggantikan seam 20 px yang direservasi di atas halaman (dibutuhkan dulu karena overlay permanen tak terlihat di atas webview level OS), dan sebelum itu dua baris permanen serta strip berlabel. Ruang yang direservasi — bukan warnanya — itulah yang membuat batas antar-pane terbaca lebar dan dinding terlihat dijahit dari kotak-kotak. Dengan webview native hilang, tak ada lagi alasan untuk kembali ke seam apa pun.
- Panel menu (`pane.menu-panel.tsx`) `position: absolute` di bawah tombol, lebar tetap 224 px, rata kanan. Satu `useEffect` di `pane.menu.tsx` memegang `suspendPanePointerCapture()` selama `open` dan melepasnya di cleanup — itu menutup **semua** jalan tutup (tombol lagi, Escape, klik luar, submit, split, pane dihapus saat menu terbuka). Jangan lepas suppressor manual per call site; menduplikasi pelepasan = depth count bocor. `useEffect` kedua memberi perilaku dropdown: fokus masuk ke field URL saat buka, balik ke tombol ⋮ saat tutup.
- **Pegangan seret pane adalah tombol ⋮, dan itu satu-satunya kandidat:** badan pane tak bisa didengar sama sekali karena iframe cross-origin menahan event di dokumennya sendiri. Ambang `DRAG_THRESHOLD_PX` = 4 px radial (`Math.hypot`) adalah seluruh pembeda antara "buka menu" dan "seret"; klik yang mengekor seret ditelan di `usePaneDragHandle` (`event.detail > 0` — klik dari keyboard `detail === 0` selalu diloloskan). Suppressor dipegang oleh **satu** `useEffect` ber-key "apakah pane ini yang sedang diseret", jadi tiap jalan keluar (drop, Escape, `window.blur`, `pointercancel`, pane dihapus di tengah seret) melepasnya sekali, tepat sekali.
- `pane.drop-overlay.tsx` hanya ada selama seret; di luar itu ia merender `null`. `pointer-events: none` di seluruhnya wajib: target drop dicari dengan `document.elementFromPoint` → `closest("[data-pane-host]")`, dan overlay yang menjawab akan membuat setiap drop mendarat di pane asal. Dipasang sebagai **sibling** `PaneFrame` di `pane.layer.tsx`, bukan anaknya — ia harus menutupi chrome pane, dan berlangganan store di sini menjaga elemen tempat halaman hidup tidak ikut re-render tiap gerak pointer.
- Aritmetika drop tinggal di `pane.drag-geometry.ts`, nol DOM: `CENTER_ZONE_FRACTION` = 0.3 → zona tengah = 40% tiap sumbu, batas antar-tepi jatuh di diagonal (sudut jadi tak memihak satu sumbu), titik di luar rect tetap jatuh ke tepi terdekat, rect degenerate → `center`. Alasan tengah dibuat lebih kecil dari empat tepi: swap memindahkan dua pane, jadi salah-swap lebih mahal daripada salah-tepi.
- **Klik kanan hanya bisa di permukaan milik app sendiri:** kotak chrome (`pane-chrome-`) dan pesan pane kosong (`pane-empty-`). Di atas konten halaman mustahil — iframe cross-origin tak pernah menyerahkan `contextmenu` ke parent. Ini batas platform, bukan pekerjaan yang terlewat.
- State `menuOpen` tinggal di `pane.frame.tsx`, bukan di `pane.menu.tsx`, karena pesan pane kosong juga membukanya.

## Jebakan test

- `bunfig.toml` mem-preload `tests/setup/happy-dom.ts`.
- **happy-dom mengukur semua elemen NOL.** Test apa pun yang menyentuh geometri atau aritmetika drag wajib `stubRect` dari `tests/fixtures/dom-rect.ts`. Geometri nyata hanya bisa diverifikasi di browser sungguhan — jangan klaim terbukti karena test hijau.
- Loading iframe dimatikan; `console.error` happy-dom soal itu difilter di setup. Pane hanya bisa diperiksa dari atribut `src`, bukan dari fetch.

Yang diuji di hilirnya (ambang, zona, panggilan store, suppressor, jalur batal) adalah kode sungguhan; yang dipalsukan cuma pengukuran. Jangan bangun rig seret kedua.

Jebakan yang sama mengenai PWA: `Response` happy-dom men-stringify body `Bun.file` jadi `[object Blob]`.
- Fixture header di `tests/fixtures/embed-headers.ts`; jangan tulis test yang menembak jaringan. `GET /api/self-test` ada supaya setup manual pun tak perlu internet.
- Tanpa test: `scripts/` dan sebagian besar `src/server/*`.

## Env & keamanan

Semua env dibaca **hanya** di `src/config/config.env.ts` — jangan baca `process.env` di tempat lain. `NOC_HOST` (127.0.0.1) · `NOC_PORT` (7788, `0` = ephemeral) · `NOC_DATA_DIR` · `NOC_DB_FILE` (noc.sqlite) · `NOC_LOG_LEVEL` (info — divalidasi tapi belum dipakai di mana pun).

**`NOC_DATA_DIR` punya dua default, dan cabangnya adalah `Bun.isStandaloneExecutable`.** Di bawah `bun run dev`/`start` tetap `.noc-data` relatif terhadap project — itu benar di sana, dan `rm -rf .noc-data` adalah reset-nya. Di binary terkompilasi, default relatif adalah jebakan: OS bisa me-launch executable dengan cwd `/` atau di mount read-only, dan itu sudah pernah terjadi (bundle `.app` menjalankan seluruh dinding dengan database di `/.noc-data/noc.sqlite`, tak bisa menyimpan apa pun). Dulu shell Rust yang menambalnya dengan mengisi `NOC_DATA_DIR` sebelum spawn; shell-nya hilang, jadi `defaultDataDir` memilih sendiri direktori per-user: `~/Library/Application Support/dev.noc.wall` (macOS), `%APPDATA%\dev.noc.wall` (Windows), `XDG_DATA_HOME` **absolut** atau `~/.local/share/dev.noc.wall` (lainnya). `XDG_DATA_HOME` relatif diabaikan sesuai spec — dan karena menghormatinya justru mengembalikan path relatif-cwd yang fungsi ini ada untuk dihindari. Nama direktorinya sengaja identik dengan identifier shell yang dihapus, supaya operator yang pernah menjalankan bundle menemukan dindingnya alih-alih mulai kosong di sebelahnya. Nilai operator selalu menang, dan nilai kosong dihitung "tak di-set" supaya `NOC_DATA_DIR=""` tak diam-diam mengembalikan jebakan ini. `readConfig(env, runtime?)` menerima runtime sebagai parameter supaya jawaban Windows bisa di-assert di macOS tanpa menyentuh variabel proses.

Loopback bukan kebetulan: `/api/embeddability` membuat server mem-fetch URL pilihan client (SSRF bila terbuka) dan layout tersimpan berisi nama dashboard internal. Bind ke `0.0.0.0` hanya atas permintaan eksplisit operator. Path database di-resolve terhadap base dir eksplisit, bukan `process.cwd()`, dan tidak boleh berada di dalam executable (`bun build --compile` menerima tulisan lalu membuangnya saat proses keluar).

## Yang belum ada

Daftar ini adalah klaim yang **belum punya bukti di layar**. Hijau di happy-dom tidak masuk hitungan (lihat "Jebakan test"). README "Open items" memuat versi panjangnya.

- **Instalasi PWA belum pernah dicoba.** Manifest, kelima rute, dan ketiga tag `<head>` sudah diverifikasi lewat HTTP dari dalam binary terkompilasi — byte-nya identik dengan `WALL_MANIFEST`, ikonnya PNG sungguhan, host proxy dijawab 404. Yang belum: tak ada browser yang pernah menawarkan install, tak ada window terinstal yang pernah dibuka, dan ikon maskable belum pernah dilihat di dock mana pun.
- **Kontrol fullscreen belum pernah tampil di layar, dan jalur multi-monitor nol coverage.** happy-dom punya satu layar primer tanpa nama dan tak punya `requestFullscreen` sama sekali — jadi justru bagian yang menjadi alasan fitur ini ada (fullscreen di monitor ketiga, bernama) adalah yang paling tak terbukti.
- **Binary: permukaan HTTP terbukti, rendering tidak.** Binary terkompilasi sudah dijalankan dari cwd `/`, menjawab 307 pendaratan, menyajikan shell + CSS + chunk JS, self-test, embeddability, dan round-trip penuh layout & saved view, lalu di-restart dan kembali dengan dinding yang sama tanpa menulis apa pun di `/`. Tapi **tak ada browser yang pernah merender dinding dari binary itu**. Enam target silang terkompilasi; hanya yang host yang pernah dieksekusi.
- **Tombol ⋮ mengambang, panel menu, seret pane, dan switcher situs: ada, ter-unit-test, nol bukti visual.** Belum diketahui: body pane benar-benar edge-to-edge, tombol terbaca di atas situs terang maupun gelap, dropdown 224 px muat di pane tersempit, ring `inset 0 0 0 1px` terbaca, label host muat di pane sempit (`max-width: 90%` + ellipsis — ellipsis yang tak menyisakan satu kata pun sama saja dengan tak ada label), ambang 4 px tidak terlalu sensitif untuk trackpad. `MAX_INLINE_SITE_PIPS` = 4 adalah tebakan di mana pip berhenti jadi target yang bisa dikenai pointer, bukan hasil pengukuran; pip 8 px + gap 4 px → baris `12n − 4` px sementara pane tersempit ~96 px (`MIN_FRACTION` 0.05 dari 1920) dan ⋮ harus muat di sebelahnya.
- **Pemecahan CSS belum pernah dilihat manusia.** Konkatenasi ketiga layer dalam urutan impor identik dengan file lama rule demi rule, dan bundle Bun keduanya hanya beda di banner path buatan Bun — tapi itu argumen tekstual, bukan tangkapan layar.
- **Pantulan dinding (rubber-band) dihilangkan secara konstruksi, bukan karena ada yang menyaksikannya hilang.** `overflow: hidden` + `overscroll-behavior: none` di `html, body, #root` menolak scroll chaining yang keluar dari iframe pane. Headless Chrome tidak melakukan rubber-band sama sekali, jadi ini hanya bisa dinilai di browser macOS sungguhan.
- **Proxy same-site: sesi terbukti bertahan di Chrome sungguhan, tapi hanya terhadap situs tiruan.** Yang sudah dilihat di layar (Chrome 155, profil sementara, perbandingan tiga arah): cookie sesi kembali di dalam pane dan bertahan melewati reload halaman dinding, kontrol di `127.0.0.1` memantul ke login seperti dulu, situs ber-`X-Frame-Options: SAMEORIGIN` + `frame-ancestors 'none'` ter-frame dan bisa login, dan dua cookie host-only terpisah per label di cookie store Chrome. Yang **belum** terbukti dan diketahui bisa pecah: tak satu pun dashboard sungguhan pernah lewat jalur ini; **URL absolut di dalam konten** (halaman yang menyusun link/XHR dari origin aslinya, bukan dari `location`) keluar dari jalur same-site dan tak ada yang menulis ulang body; situs yang **memvalidasi `Origin`/`Referer` ketat** bisa menolak dengan galat CSRF yang terlihat persis seperti bug login yang disembuhkan di sini; **websocket terautentikasi** hanya terbukti sejauh demo echo; **service worker situs** (scope per origin, jadi terdaftar di bawah label proxy) belum disentuh sama sekali; dan redirect SSO ke host pihak ketiga sengaja tak ditulis ulang.
- **Pendaratan otomatis terbukti di Chrome sungguhan**, di port terpisah bukan 7788: mengetik `http://localhost:<port>/` mendarat di `http://wall.noc.localhost:<port>/`, pane di situ berjalan dari form login → masuk → tetap masuk sesudah reload penuh, dan `?stay=1` benar-benar bertahan di `127.0.0.1`.
- **Kamera & mikrofon di pane: terbukti di Chrome sungguhan; keluhan aslinya tidak pernah terulang.** Yang sudah diukur (Chrome + kamera nyata lewat devtools protocol): pane yang mem-frame demo `@vladmandic/human` — dashboard yang dulu melooping `REQUESTED DEVICE NOT FOUND` — melaporkan `allowsFeature("camera") === true`, dua videoinput, `getUserMedia` resolve, demo sampai "starting detection"; sama di `127.0.0.1` maupun di host proxy. Melepas atribut `allow` menghasilkan `NotAllowedError`, **satu-satunya kegagalan yang bisa diproduksi repo ini, dan itu bukan `NotFoundError`.** Akar penyebab laporan aslinya **tidak diketahui**. Pembeda termurah kalau keluhan kembali: `enumerateDevices()` di dalam frame — nol perangkat = app tak pernah sempat bertanya, daftar berisi = constraint-nya yang tak cocok.
- **Setiap pane boleh minta kamera, tanpa pandang bulu.** Keputusan sadar: `allow` wall-wide karena membuatnya per-pane berarti field baru di node pane — perubahan schema, bukan toggle. Di browser pengguna tetap dapat prompt.
- **Peringatan cookie pane diam pada kasus yang paling sering.** `embed.cookies.ts` menilai `Set-Cookie` dari respons probe yang **sudah** ada di tangan — nol fetch tambahan — dan `pane.cookie-notice.tsx` menyebut nama cookie yang tak akan terkirim. Tapi probe itu satu `GET`, dan halaman login umumnya tidak men-set cookie di GET: cookie sesi lahir di `POST`, yang tak pernah dilihat server ini. Verdict `unknown` → baris tak muncul, disengaja (nol bukti = diam, bukan tebakan). **Sejak proxy mendarat, baris ini diam di seluruh jalur proxy dengan sengaja** — di sana cookie yang diperingatkan justru terkirim. Pemakai yang tersisa: dinding yang dibuka langsung di `127.0.0.1` lewat `?stay=1`.
- **Minimise & dock strip sudah dihapus dari UI, tapi `dockPane`/`undockPane` (dan `setUrlBarVisible`) tetap ada di store tanpa pemanggil UI.** Gap yang didokumentasikan, **bukan dead code** — menghapusnya merembet ke `layout.types.ts`, `layout.remove.ts`, `layout.tree.ts`, `layout.invariants.ts`, `layout.serializer.ts`, `persist.rows.ts`, `persist.migrations.ts`, dan tabel `dock`: itu perubahan schema, bukan beberes.
- Saved views: rute `/view/:viewId` dan tabel sudah ada, store view belum.
- Bug yang diketahui, belum diperbaiki: `parseWallSnapshot` menerima pane tanpa `createdAt`, jadi penyimpanannya gagal belakangan sebagai **500** (`NOT NULL constraint failed: panes.created_at`) alih-alih 400 di boundary. `scripts/binary.build.ts` memperlakukan flag asing apa pun sebagai nama target (`--minify` → `--target=bun---minify`).
